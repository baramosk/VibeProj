# 가계부 앱 데이터 흐름과 완성도

- 작성일: 2026-11-06
- 기준: `docs/planning/2026-11-06-가계부-앱.md` (확정), `docs/api-contract.md`
- 구조: 백엔드 `ledger-app/backend` (FastAPI, SQLite), 프런트엔드 `ledger-app/frontend` (React + Vite)

## 1. 전체 구조

```text
[브라우저: React + Vite]
  pages → hooks → api/client.ts
        | HTTP/JSON, HttpOnly 세션 쿠키, X-CSRF-Token 헤더
        v
[FastAPI 라우터]  api/routes/*  (입출력, 검증)
        |
        v
[서비스]  auth / category / transaction / budget / notification / report
        |
        v
[리포지토리]  repositories/*  (모든 조회에 user_id 조건)
        |
        v
[SQLite]  users, auth_sessions, categories, transactions, budgets, notifications
```

원칙:
- 화면은 데이터 로직을 직접 갖지 않고 훅을 통해서만 API를 호출합니다.
- 계산 (사용률, 금액 포맷, 날짜 경계)은 프런트 `src/lib`, 백엔드 `app/lib`의 순수 함수입니다.
- 모든 사용자 데이터는 `user_id`로 격리됩니다. 타인 리소스는 `404`입니다.

## 2. 주요 흐름

### 흐름 1. 회원가입과 로그인 (FR-01, FR-02)
1. 가입: 이메일 정규화, 형식과 비밀번호 규칙 검사 → Argon2id 해시 저장 → 기본 카테고리 복사 → 세션 쿠키와 CSRF 토큰 발급
2. 로그인: 이메일로 사용자 조회 → 잠금 확인 (10분 내 5회 실패 시 15분 잠금, `423`) → 비밀번호 검증 → 실패 횟수 초기화 → 세션 발급
3. 실패 응답 문구는 항상 같습니다. 계정 존재 여부를 숨기기 위함입니다.

### 흐름 2. 거래 저장과 예산 알림 (FR-10, FR-20, FR-21)
1. 브라우저가 `POST /api/transactions` 요청 (세션 쿠키, CSRF 헤더 포함)
2. 서비스가 입력 검증 (정수 금액, 미래 날짜 금지, 유형과 카테고리 일치)
3. 하나의 트랜잭션 안에서 거래 저장 → 영향받는 예산(전체 및 해당 카테고리, 해당 월) 사용률 계산
4. 새로 넘은 임계치 (80%, 100%)마다 알림 생성. `(예산, 월, 임계치)` 유일 제약과 `ON CONFLICT DO NOTHING`으로 중복을 막습니다.
5. 응답에 거래와 `budget_status`를 담아 화면의 예산 진행 막대를 갱신합니다.

### 흐름 3. 거래 수정과 삭제 시 재계산 (FR-12, FR-13)
1. 이전 값과 새 값에서 영향받는 (월, 카테고리) 조합을 모두 계산합니다. 월이나 카테고리가 바뀌면 두 쪽 예산을 모두 다시 계산합니다.
2. 사용률을 재계산하고, 새로 넘은 임계치에만 알림을 만듭니다.
3. 기존 알림은 취소하지 않습니다 (A-09).

### 흐름 4. 월별 리포트 (FR-14~17)
1. 월 선택 → `GET /api/reports/monthly?year_month=YYYY-MM`
2. 사용자 ID와 월 범위(Asia/Seoul 기준)로 집계: 수입 합계, 지출 합계, 잔액, 카테고리별 지출 (금액 내림차순, 0원 제외)
3. 추이: `GET /api/reports/trend?end=…&months=12`. 거래 없는 달은 0으로 채웁니다.
4. 화면: 요약 카드, 도넛 차트, 막대 차트, 같은 내용의 표 (NFR-17)

### 흐름 5. 카테고리 삭제 (FR-09)
1. 대체 카테고리가 같은 유형인지 검사
2. 하나의 트랜잭션에서 거래를 대체 카테고리로 이동 → 해당 카테고리 예산과 알림 삭제 → 카테고리 삭제
3. 중간 실패 시 전체 롤백 (테스트로 검증)

### 흐름 6. 회원 탈퇴 (FR-04)
1. 비밀번호 확인 (틀리면 `400`, `details.password`)
2. 사용자의 거래, 카테고리, 예산, 알림, 세션, 계정을 하나의 트랜잭션에서 삭제
3. 쿠키 삭제 후 로그인 화면으로 이동

### 흐름 7. 인증 요청 처리
1. 쿠키의 세션 ID로 `auth_sessions` 조회 → 만료 확인
2. 인증된 요청마다 쿠키 만료 시간 갱신 (14일 고정이 아니라 사용 시마다 연장)
3. 상태 변경 요청(POST, PUT, PATCH, DELETE)은 `X-CSRF-Token`을 세션 값과 비교 (NFR-05)

## 4. 남은 작업

1. **연동 검증:** 실제 백엔드를 띄운 상태에서 프런트 주요 흐름(가입 → 거래 기록 → 예산 알림 → 탈퇴)을 확인
2. **계약 결정:** 카테고리 유형 변경, 삭제 전 거래 수 API, 모두 읽음 API 유지 여부
3. **UX 결정:** 사용률 반올림 (99.6%를 "100%"로 보일지 내림할지), 탈퇴 시 오류 처리
4. **성능과 동시성:** 거래 10,000건 시드 후 SC-02, SC-03 측정, 동시 거래 테스트
5. **보안 보강:** 일반 API 속도 제한 (NFR-07), 만료 세션 정리 작업, Argon2 파라미터 리뷰
6. **운영:** HTTPS, 보안 헤더, 백업 보관 기간 (NFR-21), 개인정보 처리방침 (NFR-12)
7. **프런트 번들:** Recharts 지연 로딩 (현재 대시보드 진입 시 약 216kB gzip)

## 5. 알려진 위험

- 잠금 상태 응답 (`423`)과 중복 가입 응답 (`409`)으로 계정 존재 여부가 노출됩니다. 기획서에서 허용한 트레이드오프입니다.
- SQLite는 동시 쓰기에 제약이 있습니다. 개인용 MVP에는 충분하지만, 다중 사용자 운영으로 가면 PostgreSQL 전환을 검토해야 합니다.
- 프런트엔드 개발 서버와 목 API 프로세스가 아직 실행 중일 수 있습니다 (5173, 8000 포트).
