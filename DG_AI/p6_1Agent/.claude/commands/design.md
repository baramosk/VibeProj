사용자가 입력한 화면/기능 설명:

$ARGUMENTS

위 내용을 바탕으로 디자인(화면 구성, 스타일, 상호작용 상태)만 개발하세요. 모든 결과물은 한국어로 작성합니다.

## 1. 입력 확인
- `$ARGUMENTS`가 비어 있으면 어떤 화면을 디자인할지 묻고 중단합니다.
- 설명이 있으면 바로 진행합니다.

## 2. 현황 파악
- 프로젝트의 프런트엔드 구조, 스타일 방식, 디자인 토큰, 공용 컴포넌트를 읽습니다.
- 기획서(`docs/planning/`)에 해당 화면의 요구 사항이 있으면 먼저 확인합니다.
- 프런트엔드 코드가 없으면 기존 체계가 없다는 점을 기록하고, 프로젝트 기본 구성을 따릅니다. 기술 스택이 정해지지 않았다면 구현을 멈추고 사용자에게 확인합니다.

## 3. 디자인 설계
다음을 정합니다. 기획서에 없는 항목은 가정으로 명시합니다.
- **화면 구성**: 영역 배치, 주요 요소, 정보 위계
- **컴포넌트 목록**: 새로 만들 것과 재사용할 것을 구분
- **상태 정의**: 기본, 로딩, 빈 상태, 오류, 성공, 비활성
- **상호작용**: hover, focus, active, disabled와 전환 효과
- **반응형**: 모바일, 태블릿, 데스크톱 레이아웃
- **접근성**: 명도 대비(WCAG AA), 키보드 탐색 순서, 포커스 표시, 대체 텍스트, 의미 있는 마크업

## 4. 디자인 개발 (ui-designer 에이전트 위임)
- `ui-designer` 에이전트에 3단계 설계를 전달하고 구현을 맡깁니다.
- 다음 원칙을 지시합니다.
  - 기존 디자인 토큰과 공용 컴포넌트를 우선 사용하고, 새 색상과 간격 값을 임의로 만들지 않습니다.
  - 비즈니스 로직, API 호출, 데이터 처리는 만들지 않습니다.
  - 데이터가 필요한 부분은 props나 더미 데이터로 채우고, 실제 연결 지점을 주석 한 줄로 표시합니다.
  - 이벤트 핸들러는 빈 자리만 두고, 동작은 구현하지 않습니다.
  - 테스트가 쓸 식별자(`data-testid` 등)를 붙여 둡니다.
- 구현 범위는 요청한 화면과 컴포넌트에 한정합니다.

## 5. 검증
- 빌드와 린트를 실행합니다. 실패하면 디자인 변경 때문인지 확인하고 고칩니다.
- 기존 테스트가 깨지지 않았는지 확인합니다.
- 가능하면 화면을 열어 캡처하고, 다음을 확인합니다.
  - 모바일 폭에서 레이아웃이 깨지지 않는지
  - 텍스트와 배경의 명도 대비가 기준을 넘는지
  - 키보드만으로 모든 요소에 접근할 수 있는지
- 실행하지 못한 항목은 그 사실을 명시합니다.

## 6. 제한 사항
- 로직, API, 데이터 처리는 만들지 않습니다.
- 요청 범위 밖의 화면은 고치지 않습니다.
- 공용 스타일을 바꿔 다른 화면에 영향이 가면 구현을 멈추고 보고합니다.
- 커밋, 푸시는 사용자가 요청할 때만 합니다.

## 7. 최종 응답
다음을 간결하게 보고합니다.
1. 디자인한 화면과 컴포넌트 목록 (새로 만든 것 / 재사용한 것)
2. 정의한 상태와 반응형 기준
3. 변경 파일 목록
4. 연결 지점: 나중에 로직을 붙일 위치와 필요한 데이터 형태
5. 검증 결과 (빌드, 린트, 캡처 확인 여부)
6. 남은 과제와 사용자가 결정해야 할 디자인 항목 (권장 답안 포함)
