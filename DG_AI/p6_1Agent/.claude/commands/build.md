사용자가 입력한 구현 대상 기능:

$ARGUMENTS

위 기능을 서브 에이전트에게 나누어 맡겨 실제로 구현하세요. 모든 결과물과 보고는 한국어로 작성합니다.

## 1. 입력 확인
- `$ARGUMENTS`가 비어 있으면 어떤 기능을 구현할지 묻고 중단합니다.
- 설명이 있으면 바로 진행합니다.

## 2. 기획 확인
- `docs/planning/`에서 이 기능과 관련된 기획서를 찾습니다.
- 기획서가 없거나 상태가 "초안"이면, `planner` 에이전트를 호출해 기획서를 먼저 만들게 합니다. 기획서가 "확정"될 때까지 구현 단계로 넘어가지 않습니다. 열린 질문이 있으면 사용자에게 확인합니다.
- 기획서가 있으면 구현할 FR 목록과 완료 조건을 정리합니다.

## 3. 구현 계획
- 기능을 작업 단위로 나눕니다. 각 단위에 담당 에이전트(`developer` 또는 `ui-designer`)를 정합니다.
- 같은 파일을 여러 에이전트가 고치지 않도록, 서로 독립인 단위만 병렬로 맡깁니다.
- 계획을 짧게 보고한 뒤 진행합니다.

## 4. 로직 구현 (developer 서브 에이전트)
`developer` 서브 에이전트를 호출해 다음을 맡깁니다.
- 전달 내용: 기능 설명, 기획서 경로, 구현할 FR ID, 관련 기존 파일
- 요구 사항:
  - 계층 분리(입출력, 비즈니스 로직, 데이터 접근)와 인터페이스 기반 의존성 주입
  - 설정 값의 외부화, 비밀 값의 코드 밖 보관
  - 테스트 추가 (테스트 이름에 FR ID 포함)
  - 기존 공개 인터페이스를 깨뜨리지 않기
- 결과 보고를 받은 뒤 변경 파일을 읽고, 기획과 어긋나지 않는지 확인합니다.

## 5. UI 구현 (ui-designer 서브 에이전트)
- 화면이 있는 기능이면 `ui-designer` 서브 에이전트를 호출합니다.
- 전달 내용: 대상 화면 파일, 기획서의 UI 요구 사항
- 요구 사항: 로직과 API는 건드리지 않고, 표현 계층만 다듬기. 테스트 식별자 유지.
- 화면이 없는 기능이면 이 단계를 건너뛰고 그 사실을 보고합니다.

## 6. 검증
- 프로젝트의 테스트, 린트, 타입 검사 명령을 실행합니다. 명령이 없으면 어떤 도구를 쓸지 보고합니다.
- 실패하면 원인을 파악해 해당 서브 에이전트에게 수정을 다시 맡깁니다. 테스트를 약화하거나 건너뛰지 않습니다.
- 기획서의 검증 계획 항목을 하나씩 확인합니다.

## 7. 제한 사항
- 요청한 기능 범위 밖의 코드는 고치지 않습니다.
- 기획서에 없는 기능을 추가하지 않습니다.
- 기존 공개 인터페이스를 깨뜨려야 하면 구현을 멈추고 사용자에게 확인합니다.
- 커밋, 푸시, 파괴적 삭제는 사용자가 명시적으로 요청할 때만 합니다.

## 8. 최종 응답
1. 구현한 기능과 FR ID
2. 서브 에이전트별 작업 내역 (developer, ui-designer)
3. 변경 파일 목록
4. 검증 결과 (실행한 명령과 통과/실패 여부, 미실행 항목 명시)
5. 남은 작업, 위험, 사용자가 결정해야 할 항목 (권장 답안 포함)
