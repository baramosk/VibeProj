사용자가 입력한 기능/프로젝트 설명:

$ARGUMENTS

위 내용을 바탕으로 다음 순서로 작업하세요. 모든 결과물은 한국어로 작성합니다.

## 1. 입력 확인
- `$ARGUMENTS`가 비어 있으면 무엇을 만들지 묻고 중단합니다.
- 설명이 있으면 바로 진행합니다.

## 2. 요구 사항 분석 (planner 에이전트 위임)
- `planner` 에이전트를 호출하여 설명을 요구 사항 정의서로 구체화하게 합니다.
- 산출물: 배경, 목표, 성공 기준, FR/NFR, MVP 범위, 가정, 열린 질문(권장 답안 포함).
- 기획서는 `docs/planning/YYYY-MM-DD-<주제-slug>.md`에 저장합니다.

## 3. 설계
- 기술 스택, 주요 모듈, 계층, 데이터 흐름을 설계합니다.
- 기존 프로젝트 파일이 있으면 먼저 읽고, 이미 정해진 스택과 규칙을 따릅니다.
- 확장 지점(변형이 예상되는 부분)과 그 근거를 기획서에 적습니다.

## 4. 폴더 구조 설계 및 생성
- 설계에 맞춰 디렉터리 트리를 정하고, 각 폴더와 주요 파일의 역할을 한 줄씩 기획서에 적습니다.
- 이 단계에서 폴더와 빈 파일 골격을 실제로 만듭니다. 기존 파일은 덮어쓰지 않습니다.
- 기존 프로젝트와 구조가 충돌하면 멈추고 사용자에게 보고합니다.

## 5. 구현 (developer 에이전트 위임)
- 기획서의 FR을 우선순위 순서대로 `developer` 에이전트에 하나씩 또는 작은 묶음으로 맡깁니다.
- 각 단위마다 다음을 요구합니다.
  - 계층 분리와 인터페이스 기반 의존성 주입
  - 설정 값의 외부화, 비밀 값의 코드 밖 보관
  - 테스트 이름에 FR ID 포함
- 구현 중 기획서와 어긋나는 부분이 생기면 임의로 바꾸지 말고 기록한 뒤 보고합니다.

## 6. 검증
- 프로젝트의 테스트, 린트, 타입 검사 명령을 실행합니다. 명령이 없으면 어떤 도구를 쓸지 기획서에 기록하고 보고합니다.
- 실패한 항목은 원인을 고쳐 다시 실행합니다. 테스트를 약화하거나 건너뛰지 않습니다.
- 실행하지 못한 항목은 그 사실을 명시합니다.

## 7. 제한 사항
- 기획서에 없는 기능을 추가하지 않습니다.
- 기존 공개 인터페이스를 깨뜨려야 하면 구현을 멈추고 사용자에게 확인합니다.
- 커밋, 푸시, 파괴적 삭제는 사용자가 명시적으로 요청할 때만 합니다.

## 8. 최종 응답
다음을 간결하게 보고합니다.
1. 기획서 경로
2. 핵심 요구 사항 요약 (5줄 이내)
3. 폴더 구조 트리와 각 역할
4. 구현한 FR 목록과 변경 파일 목록
5. 검증 결과 (실행한 명령과 통과/실패 여부)
6. 남은 작업, 위험, 사용자가 결정해야 할 열린 질문 (권장 답안 포함)
