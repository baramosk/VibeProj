## 2. 세 가지의 관계

- **`/planner` 명령은 진입점**입니다. 사용자는 명령만 입력하고, 명령 안의 지시문이 메인 세션에게 작업 순서를 알려줍니다.
- **`planner` 에이전트는 작업자**입니다. 명령이 요구 사항 분석을 이 에이전트에 위임합니다.
- 명령은 에이전트 결과에 **설계와 폴더 구조 제안**을 더합니다. 에이전트는 요구 사항 분석까지만 맡습니다.
- 즉 `/planner`는 `planner` 에이전트를 포함하는 상위 흐름입니다.

```text
/planner [설명]  ──▶  메인 세션 (명령 지시문 실행)
                        ├─ 2단계: planner 에이전트 ──▶ 요구 사항 분석
                        ├─ 3단계: 설계 (메인 세션)
                        ├─ 4단계: 폴더 구조 제안 (메인 세션)
                        └─ 5단계: docs/planning/ 에 기획서 저장
```

## 3. 기본 `Plan` 에이전트와의 차이

- **질문의 층위가 다릅니다.** `planner`와 `/planner`는 "무엇을 만들지"를 정하고, `Plan`은 "이미 정해진 것을 어떻게 만들지"를 정합니다.
- **결과물 보존 방식이 다릅니다.** `planner`와 `/planner`는 기획서 파일을 남기지만, `Plan`은 응답으로만 돌려주고 파일을 남기지 않습니다.
- **모호함을 다루는 방식이 다릅니다.** `planner`는 가정을 명시하고 결정이 필요한 항목을 열린 질문으로 분리하며 권장 답안을 붙입니다. `Plan`은 주로 코드베이스를 근거로 계획을 세웁니다.
- **외부 정보 확인 여부가 다릅니다.** `planner`는 웹 검색으로 기술 사양과 출처를 확인하도록 되어 있습니다. `Plan`은 기본적으로 코드베이스 중심입니다.
- **출력 형식이 다릅니다.** `planner`는 FR/NFR, 범위, 가정, 열린 질문 등 고정된 12개 섹션을 씁니다. `Plan`은 단계별 구현 계획, 핵심 파일, 설계 트레이드오프를 제시합니다.

> 참고: `Plan`의 내부 프롬프트 전문은 확인할 수 없어, 위 내용은 도구 설명에 나온 기능을 기준으로 정리했습니다.

## 4. 기타 혼동 지점

- **Plan 모드(`EnterPlanMode`)는 에이전트가 아닙니다.** 메인 세션의 작업 모드로, 파일을 수정하지 않고 계획만 세운 뒤 승인을 받는 방식입니다.
- **이름 충돌 가능성:** `planner`와 `Plan`은 철자가 달라 구분되지만, 대소문자만 다른 이름은 혼동될 수 있어 피했습니다.
- **명령과 에이전트의 이름이 같습니다.** `/planner`(명령)와 `planner`(에이전트)가 같은 이름을 쓰지만, 호출 경로가 달라 실제 사용에는 문제가 없습니다.

## 5. 사용 기준

| 상황 | 추천 |
|---|---|
| 새 프로젝트나 기능을 처음 정리할 때 (요구 사항 + 설계 + 폴더 구조 전부 필요) | `/planner [설명]` |
| 요구 사항만 빠르게 정리하고 싶을 때 | `planner` 에이전트 |
| 요구 사항이 이미 정해졌고 기존 코드에 구현 방법을 묻고 싶을 때 | `Plan` 에이전트 |
| 기획서로 정리된 뒤 실제 구현 순서를 짜고 싶을 때 | `planner` 기획서를 근거로 `Plan` 호출 |

## 6. 권장 흐름

1. `/planner [설명]`으로 요구 사항, 설계, 폴더 구조가 담긴 기획서를 만듭니다.
2. 기획서의 열린 질문에 답하고 상태를 "확정"으로 바꿉니다.
3. 확정된 기획서를 근거로 `Plan` 에이전트에 구현 계획을 맡깁니다.
4. 승인 후 폴더를 생성하고 구현합니다.
